# 04 — 重写设计方案

## 目标架构：Rust 后端进程 + 薄 QML 前端

```
┌─────────────────────────────────────────────────────┐
│ Quickshell (插件 crmne.lyrics 对标品, id: local.lyrics-rs) │
│                                                     │
│  Service.qml ─┐                          BarWidget.qml
│  (薄壳:拉起/   │  stdio JSON (行式, serde_json)   │
│   监控后端)    ├◀──────────────────────────────▶│
│               ▼        LyricsView.qml            │
│        ┌──────────────────────────┐               │
│        │  lyricsd (Rust 单二进制)   │               │
│        │  • zbus: MPRIS 监听        │               │
│        │  • reqwest: LRCLIB 客户端  │               │
│        │  • 播放进度→当前行计算       │               │
│        │  • 5s 心跳 + 状态日志       │               │
│        └──────────────────────────┘               │
└─────────────────────────────────────────────────────┘
```

**原则：所有"会出 bug 的逻辑"（DBus、HTTP、时间同步、类型解析）都在 Rust；QML 只做渲染和点击，QML 里禁止业务逻辑。**

## Rust 后端（lyricsd）

- 位置：本仓库 `backend/`，edition 2024，产出单二进制。
- crate 选型（与用户已有工具保持一致的口味）：
  - `zbus`（或 `mpris-rs`）— MPRIS/DBus
  - `reqwest`（rustls，别拉 openssl）+ `serde_json` — 歌词源
  - `tokio` runtime
  - 日志：`tracing` + 写本地文件（quickshell 日志抓不到子进程 stderr，**必须落盘**，建议 `~/.local/state/omarchy-lyrics-rs/log`）
- 歌词源与择优链（2026-10-31 用户拍板：v1 直接上词级卡拉OK；同日真机定源）：
  1. **词级主源**：`https://lrc.red/api/v1?q=<title+artist>`（Apple Music TTML）——真机验证多次命中粤语/国语歌，质量好
  2. **词级副源（并发占位）**：`https://www.karalyr.com/api/get`（开放卡拉OK库，API 形状与 LRCLIB 兼容，只服务词级，syncedLyrics 为 Enhanced LRC，parse_lrc 直接消化）——2026-10-31 探测覆盖率≈0，先接入等库长大；binimum.org 同日实测 307 重定向到 lrc.red（同一家），已退役
  3. **LRCLIB 词级（待接入）**：官方已上线 `hasWordSync`/`lyricsfile`（YAML，词级在 lines[].words），2026-10-31 采样 100+ 热门歌覆盖为 0，等有真实样例再写解析器；接入时作为第四路并发
  4. **行级降级**：LRCLIB `/api/get` 精确 → `/api/search` 兜底；候选打分与元数据清洗规则整体移植自原插件 Model.js（见 docs/02 源码实读 #7）；LRCLIB 高峰间歇 503 已加 5xx 退避重试
  5. **纯文本兜底**：LRCLIB plainLyrics，按 duration 等分模拟时间轴
  - 择优顺序：词级 > 行级 > 纯文本；词级三路并发，先到先得
  - 所有请求带自定义 `User-Agent`（`omarchy-lyrics-rs/<version>`），LRCLIB 官方要求此头
- 位置推算：MPRIS `Position` 不连续更新，用 `Rate` + 单调时钟外推，`Seeked` 信号与 rate 变更时重新锚定；对外只推行变更/词变更事件，QML 不做时间计算。
- IPC：**行式 JSON over stdio**（Service.qml 用 `QuickProcess`/`Process` 拉起后端并逐行读）。消息类型见下。**定案（2026-10-31）**：BarWidget 不自己拉后端，经 `bar.shell.serviceFor("local.lyrics-rs")` 读 Service 实例的属性共享状态（原插件与 rosakodu.dock 在本机验证过的机制）；unix socket 只留作 Process 组件翻车时的备选（见 docs/05 风险节）。
- 后端自身状态持久化：`~/.local/state/omarchy-lyrics-rs/`（日志、LRCLIB 缓存）。

### stdio 协议（每行一个 JSON 对象）

后端 → QML：
```jsonc
{"ev":"track","artist":"...","title":"...","album":"...","durationSec":213.5,"artUrl":"..."}
{"ev":"lines","synced":[[12.3,"第一句",[["第",12300],["一",12800],["句",13300]]],...],
 "plain":"备用全文","source":"word|lrclib|cache|none"}   // synced 每行可带词级时间轴(ms)，无词级则为 null
{"ev":"line","index":12,"text":"第一句","rich":"<b>第一</b>句"}  // 当前行变更时推；rich 为 StyledText，已唱词加粗
{"ev":"word","index":2}          // 行内当前词下标变更（卡拉OK逐词点亮用）
{"ev":"position","sec":45.2,"playing":true}   // 1Hz，进度条/时间显示用
{"ev":"status","msg":"lrclib_unreachable"}     // 降级/错误通知，QML 显示兜底文案
{"ev":"backend","msg":"started|lyricsd_missing"} // Service 拉起结果，缺二进制必须显式上报，禁止静默
```
QML → 后端：
```jsonc
{"cmd":"refresh"}        // 手动换歌/重查（忽略缓存）
{"cmd":"trackId","id":"..."}  // (可选) 用户在候选里选了另一版歌词
```

## QML 前端（插件目录 `plugin/`）

- `manifest.json`：照抄 docs/02 的契约，改 id 为 `local.lyrics-rs`，`kinds: ["service","bar-widget"]`，`entryPoints` 同构；`barWidget.schema` 保留同样的三个设置键（`hideWhenIdle` / `panelWidthPercent` / `panelHeightPercent`）保证用户设置语义一致。
- `Service.qml`：`Component.onCompleted` 拉起 `lyricsd`（路径约定：`~/.local/bin/lyricsd`），后端退出时自动重启（指数退避，上限 30s），**每次重启写一条日志**。
- `BarWidget.qml`：紧凑态 = **封面缩略图（约 20px 圆角）+ 当前行歌词条**（2026-10-31 用户拍板并二次确认：**Omarchy 顶栏原生扁平风格，不做 DMP 胶囊**——胶囊是 GNOME 悬浮 overlay 的形，塞进 30px 扁平顶栏违和；只借 DMP 的交互基线，视觉跟 ActiveWindow/Clock 同语言）。行文本绑定 service 的 `lineRich`/`lineText`（StyledText，已唱词加粗），行变更宽度动画过渡；`hideWhenIdle` 判断必须写死成类型归一化（`v === true || v === "true"`，见 docs/03 教训 #1）并 `console.log` 实际读到的值；主题色从 Omarchy 主题注入的 `Color` 对象取，禁止硬编码颜色（本机昼夜主题自动切换，硬编码必翻车——参照 dock 插件跟色的方式）。
- `Service.qml` 与 BarWidget 共享状态：Service 解析 stdio 事件后写入自身属性（`track`/`lines`/`lineIndex`/`lineRich`/`lineText`/`wordIndex`/`playing`/`status`），BarWidget 经 `bar.shell.serviceFor("local.lyrics-rs")` 直接读（原插件同款机制，见 docs/02 源码实读 #4）。
- `LyricsView.qml`：QML `ListView` 实现，不照抄 DMP 的 Cairo 自绘——delegate 按 `index - lineIndex` 距离绑 opacity/scale，`Behavior` 平滑跟随当前行；手动滚动进浏览模式（2.5s 自动回跟随 + "回到当前行"按钮）；词级歌显示逐词高亮（`wordIndex` 驱动），行级歌退化为整行高亮；点击行跳播（若 MPRIS 支持 SetPosition/CanSeek；不支持就隐藏跳播入口）。

### 交互设计基线（金标准：Dynamic Music Pill，详见 docs/07）

1. **点击封面/部件展开歌词面板**（不是 hover，不是额外按钮）
2. **LyricsView 双模式滚动**：默认自动跟随当前行；用户手动滚动后进入浏览模式，出现"回到当前行"机制
3. **点击歌词行 seek**（MPRIS SetPosition 可用时启用）
4. 当前行强调：金标准是粗体白色，本项目用主题强调色 + 粗体
5. 波形可视化动画 **v1 不做**（成本高；用户点名再加）

## 与原插件的功能对齐表

| 功能 | 原插件 | 重写版 |
|------|--------|--------|
| MPRIS 取轨 | Service.qml | lyricsd (zbus) |
| 歌词获取 | bin/lrclib (Python) | lyricsd (reqwest) |
| 逐行高亮 | Model.js + QML | lyricsd 算当前行/当前词，QML 只渲染（词级卡拉OK v1 就上，2026-10-31 用户拍板） |
| 封面 | bin/artwork (Python) | lyricsd 透传 artUrl，QML 直接加载（加大小上限）|
| 无词降级 | ? | 明确：显示"暂无歌词"，部件不消失 |
| 设置项 | 3 个 | 同 3 个，读取强制归一化 |

## 明确不做（v1 范围外）

- 多播放器并行选择 UI（v1 只取第一个活跃 MPRIS player，与原插件一致）
- 歌词翻译/罗马音
- 本地歌词文件加载
- NetEase/QQ 音乐词源（LRCLIB 覆盖不了的歌 v1 就让它显示"暂无歌词"）
