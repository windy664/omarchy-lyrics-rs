### 阶段 1 验收登记（2026-10-31，真机 Spotify）

| # | 结果 | 证据与备注 |
|---|------|-----------|
| 1.1 | ✅ | busctl 驱动切歌 6+ 次（祇想一生跟你走→無盡空虛→遇見→傳聞→黑白照→記事本→Today→記憶棉→匆匆那年），每次都发新 `track` 事件并重查；Spotify 广告（"A brief message from our sponsor."）正确走 `no_lyrics` 分支 |
| 1.2 | ✅ | 词级 `word:lrc.red` 多次真机命中（無盡空虛/傳聞/Today/記憶棉/匆匆那年，行内带 `words` 毫秒级时间戳）；LRCLIB 行级命中（祇想一生跟你走 23 行 synced）；查不到时发 `{"ev":"status","msg":"no_lyrics"}`，无 panic |
| 1.3 | ✅ | `position` 每秒推进（sec 单调）、`line` 事件随播放逐行逐字推进（`index`+`word` 索引、rich markup 已唱加粗/未唱置灰）；暂停发出 `{"ev":"position","playing":false}` 且 sec 冻结 |
| 1.4 | ✅ | 日志落盘正常（含 lookup spawned/done、fetch result、stale drop）；`cargo build --release` 零 warning，单测 6/6 绿 |

**验收过程中发现并修复的两个真 bug**：

1. **position 冻结**：zbus 生成 proxy 默认 `CacheProperties::Lazy`，Position 首读后靠 `PropertiesChanged` 更新缓存，而 Spotify 从不发 Position 的 changed 信号 → `position()` 永远返回首读值。修复：`build_player`/`peek_player` 显式 `.cache_properties(zbus::CacheProperties::No)`。
2. **过期查询结果覆盖新歌词**：换曲后旧 track 的查询结果（最长 12s 兜底窗口）迟到，把新 track 刚载入的 `lines` 清空并误发 `no_lyrics`（真机复现：越難越愛→Today）。修复：`FetchResult` 增加 `generation` 代号，换曲/refresh 时 `lookup_gen += 1`，收到不匹配的结果按 stale 丢弃。

**新登记的外部风险**：LRCLIB 高峰期间歇 503（ServerOverloaded），真机当日多次复现，导致《遇見》《記事本》瞬时查不到。已缓解：`get_text` 对 5xx 做 2 次退避重试（800ms/1.6s）；残余风险是持续 503 窗口内该曲本轮查不到，等下轮换曲或 refresh 可恢复，缓存目录不受影响。

### 广告字幕真相（2026-10-31，v0.2.4 修复）

**顶栏广告字幕自 v1 起从未生效过**，且静默无报错。根因：`isAd` 定义在 Text 元素内部，而 text 绑定写的是 `root.isAd`——QML 访问 QObject 不存在的属性**静默返回 undefined**，falsy → 永远走歌词分支。后端识别、Service 状态、status IPC 全部正常，唯独绑定读错了对象。修复：`isAd` 提升到 BarWidget root。排查中另修两处：Service 换曲时不清 `lineRich`（广告期间顶栏残留上一首歌词行）；status IPC 补 status/statusMsg 字段（排查利器）。验证：真实 Bose 广告在顶栏渲染出广告文案（OCR 截图实锤），广告轮换（Bose→Pandora）实时跟踪。

**教训**：QML 绑定引用不存在的属性不报错、不告警，直接 falsy——属性提升/改名时必须全局搜引用；`readonly property` 挂错层级比拼错名字更隐蔽。
